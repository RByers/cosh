Chromium Open Source Health

One way to judge the health and stability of an open source project is to look at the relationship between each stakeholder's investment in it and the value it gets out of it. When that value exchange is far out of balance, it can lead to a rupture in the project community. Quantifying this value exchange is generally very difficult, but Chromium makes an approximation possible. The value a browser gets from its engine is roughly proportional to that browser's usage. Evaluating investment level is more difficult. Today, a primary cost of maintaining a large open source project is the effort of directing how the codebase evolves. AI coding agents have made code cheap to write, which makes deciding what should and shouldn't land in the project even more valuable. Code review is therefore a reasonable proxy for an organization's investment in a large open source project.

This page approximates that value exchange by comparing each organization's share of Chromium-based browser usage (according to Cloudflare Radar) with its share of Chromium code reviews.

Review by organization

Scale

What's counted. Review comments on chromium/src CLs targeting main, each in the ISO week it was written, on merged, abandoned and still-open CLs (review that stops a CL from landing still counts). Only CLs owned by humans are included, so autorolls and other bot commits are left out. Comments by bot and AI-agent accounts are dropped too, as are owners' comments on their own CLs. Comments that a reviewer posts with AI help count like any other comment from that reviewer. Only comments on the paths listed under Review by directory count.

Metrics. All three come from review comments. Reviews with no comment, such as a bare +1 vote, don't count: there is no way to tell how much review went into them. Review comments are published comments, inline or patchset-level, including those written after the CL landed (the table below also shows how many of those there are). Comments that declare themselves AI-generated are included (the table also shows how many there are). Review characters is the length of those comments with quoted (>) lines removed. Reviewed CLs counts, in the week each CL closed, the CLs where someone from the organization commented; open CLs count once they close.

Organization. Each reviewer is assigned to an organization as of the date of the comment (for reviewed CLs, the date the CL closed), using the first rule that applies: (1) if the reviewer is listed in Chromium's own affiliations.json5, the affiliation in effect on that date is used. This lets an @chromium.org or personal address count for the person's employer, and follows people who change employers; (2) other @chromium.org accounts count as Google (google.com); (3) everyone else counts for their email domain, with Meta's old fb.com merged into meta.com. The chart shows the organizations with the most review; the rest, including gmail.com addresses, are combined as “Other”.

Chromium browser usage (Cloudflare Radar)

The ratio's denominator: each browser's share of Chromium-based browser usage, including Android WebView and in-app browsers. Human traffic, complete ISO weeks, iOS excluded. Facebook and Instagram (Meta's whole usage credit) are always shown; the rest of the small browsers are combined as “Other”. The ratio leaves out ChromeDerivative (see the note below).

WebViews and in-app browsers. Pages opened inside apps count as Chromium usage. Android System WebView (ChromeMobileWebview), the Chromium engine Google ships for apps, is credited to Google along with Chrome. The Facebook and Instagram in-app browsers are credited to Meta, and Microsoft 365's to Microsoft. Other in-app browsers (Snapchat, Pinterest and others) stay in the denominator but are credited to no organization.

iOS is excluded. Every iOS browser, Chrome included, must use Apple's WebKit engine, and in-app browsers there use WKWebView, so Chromium is barely used on iOS. Radar can't filter iOS out directly, so each day's iOS traffic is subtracted from the all-platform figures using Radar's iOS-only browser breakdown and iOS share of requests.

Brave is excluded. Brave sends Chrome's User-Agent string and names itself only in the Sec-CH-UA client hint. Radar reports it at about 0.002% of Chromium usage, roughly a thousand times below Brave's real size, so Brave's usage is unknown and is most likely counted as Chrome. brave.com therefore gets no usage share or value ratio. If Brave's real share was moved out of Chrome, Google's usage share would be a few points lower and its value ratio slightly higher.

Note on ChromeDerivative. Radar's bucket for Chromium-based browsers it can't name jumped from about 0.3% to about 10% of Chromium usage starting in 2026-W37 (on 9 September 2026). It came from every browser in proportion, Safari and Firefox included, not mostly from Chrome. It looks like Radar started labeling traffic it previously couldn't identify, possibly real Chromium-based browsers; Cloudflare hasn't explained it. Until that is explained, the value ratio and the table's usage shares leave the bucket out: each organization's usage share is its share of the other Chromium usage. This chart still shows the bucket.

Review by directory

    Which paths count. The value ratio, the organization chart, the table and the leaderboard count only review comments on these chromium/src paths (the longest matching rule wins):

      chrome/, ios/, android_webview/, ash/ and chromeos/ hold Google's own products built on Chromium: the Chrome browser, Chrome for iOS, Android WebView and ChromeOS. Review there is mostly Google reviewing Google's product code, so it says little about who maintains the engine other browsers share. components/ is mostly browser features built for Chrome, such as autofill, sign-in and enterprise reporting; over a year, 98% of its review comments came from Google. chrome/browser/web_applications/ and chrome/browser/webnn/ are shared platform work that other Chromium browsers build on; components/viz/ (the compositor) and components/services/storage/ (the storage backend for localStorage and sessionStorage) are part of the engine. Those stay in. Everything else counts.

      Placing comments on a file. Gerrit doesn't give us each CL's file list, so an inline comment counts for its own file, and a patchset-level comment counts for the file on the same CL with the most inline comments (from anyone, including the CL's owner). A CL whose comments are all patchset-level can't be placed; its comments show as (no file) above and are left out of the other charts.

      Why only review tied to source files. Comments that can't be placed are mostly sign-offs, not review that can be weighed: in a sample, 43% were just “LGTM”, “thanks” or similar, against 4% of inline comments, and reading 30 such CLs at random found real review discussion on only 4. A reviewer who digs into the code usually comments on a line of it, so review attached to source files is the better measure of real investment. Leaving these comments out barely changes any organization's share.
