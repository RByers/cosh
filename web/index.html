Chromium Open Source Health

One way to judge the health and stability of an open source project is to look at the relationship between each stakeholder's investment in it and the value it gets out of it. When that value exchange is far out of balance, it can lead to a rupture in the project community. Quantifying this value exchange is generally very difficult, but Chromium makes an approximation possible. The value a browser gets from its engine is roughly proportional to that browser's usage. Evaluating investment level is more difficult. Today, a primary cost of maintaining a large open source project is the effort of directing how the codebase evolves. AI coding agents have made code cheap to write, which makes deciding what should and shouldn't land in the project even more valuable. Code review that shapes what lands is therefore a reasonable proxy for an organization's investment in a large open source project. Not every review comment is an investment, though: some cost the author time without changing anything.

This page approximates that value exchange by comparing each organization's share of Chromium-based browser usage (according to Cloudflare Radar) with its share of addressed review comments: comments in review threads that led the change's author to modify the change. That is decided from the author's replies, with an AI model reading the threads where the reply alone doesn't settle it (how, and how accurately). Chromium is roughly divided into infrastructure/engine code (e.g. content, blink) shared by every Chromium-based browser, and Google Chrome product code (e.g. chrome/browser/ui), so we focus here on the former only. Chrome product code is reviewed almost entirely by Google for Google's own product, so counting it would inflate Google's share of investment in the shared engine. This analysis should be treated as a rough approximation only, with trends over time likely more meaningful than absolute values at any point in time.

Scale

What's counted. Review comments on chromium/src CLs targeting main, each in the ISO week it was written, on merged, abandoned and still-open CLs (review that stops a CL from landing still counts). Only CLs owned by humans are included, so autorolls and other bot commits are left out. Comments by bot and AI-agent accounts are dropped too, as are owners' comments on their own CLs. Comments that a reviewer posts with AI help count like any other comment from that reviewer. Only comments on the paths listed under Review by directory count.

Metrics. All four come from review comments. Reviews with no comment, such as a bare +1 vote, don't count: there is no way to tell how much review went into them. Addressed comments, the primary metric, are the review comments in a thread that led the CL's owner to change the CL (how that is decided is below); weeks not yet classified show the other metrics only. Review comments are published comments, inline or patchset-level, including those written after the CL landed (the table below also shows how many of those there are). Comments that declare themselves AI-generated are included (the table also shows how many there are). Review characters is the length of those comments with quoted (>) lines removed. Reviewed CLs counts, in the week each CL closed, the CLs where someone from the organization commented; open CLs count once they close.

How addressed comments are classified, and how accurate it is

A thread is a reviewer's comment plus every reply to it. A thread is addressed if the feedback led the CL's owner to change the CL itself: code, tests, code comments, build files or the commit message. Adopting part of a suggestion, making a different or better change because of it, adding a TODO, or moving code out of the CL all count. It is not addressed if the owner answered a question, explained or pushed back; if the comment was an approval, thanks or FYI; if the work went to another CL or a bug; or if the reply was a bare “Acknowledged”.

Each thread is decided in this order. (1) If the owner never replied, or started the thread, it scores nothing. (2) If the owner's first reply starts with “Done”, “Fixed”, “Fix applied.” or similar, it is addressed. (3) Otherwise Claude Haiku reads the whole thread and decides. Every comment in an addressed thread that isn't the owner's, up to the owner's last reply, earns its author one point: a reviewer who goes back and forth earns more, and so does a second reviewer who joins in.

Accuracy. Measured on 400 random threads with an owner reply (CLs closed 2026-W36 to 2026-W44), labelled by Claude Haiku and checked by Claude Opus: the regex plus Haiku, as used here, has a precision of 0.97 and a recall of 0.99 (accuracy 0.97). The regex alone has a precision of 0.98 but a recall of only 0.78: it misses changes described in free text. About 2% of threads are ambiguous even to a careful reader. The production prompt shows the model whole threads (the evaluation showed the first nine replies) and has not been re-measured; of 12 production labels checked by hand, 11 were right and 1 was unclear. These figures are per thread. Points are per comment, so long threads weigh more. Details are in docs/comment-classifier.md.

Organization. Each reviewer is assigned to an organization as of the date of the comment (for reviewed CLs, the date the CL closed), using the first rule that applies: (1) if the reviewer is listed in Chromium's own affiliations.json5, the affiliation in effect on that date is used. This lets an @chromium.org or personal address count for the person's employer, and follows people who change employers; (2) other @chromium.org accounts count as Google (google.com); (3) everyone else counts for their email domain, with Meta's old fb.com merged into meta.com. The chart shows the organizations with the most review; the rest, including gmail.com addresses, are combined as “Other”.

Chromium browser usage (Cloudflare Radar)

The ratio's denominator: each browser's share of Chromium-based browser usage, including Android WebView and in-app browsers. Human traffic, complete ISO weeks, iOS excluded. Facebook and Instagram (Meta's whole usage credit) are always shown; the rest of the small browsers are combined as “Other”. The ratio leaves out ChromeDerivative (see the note below).

WebViews and in-app browsers. Pages opened inside apps count as Chromium usage. Android System WebView (ChromeMobileWebview), the Chromium engine Google ships for apps, is credited to Google along with Chrome. The Facebook and Instagram in-app browsers are credited to Meta, and Microsoft 365's to Microsoft. Other in-app browsers (Snapchat, Pinterest and others) stay in the denominator but are credited to no organization.

iOS is excluded. Every iOS browser, Chrome included, must use Apple's WebKit engine, and in-app browsers there use WKWebView, so Chromium is barely used on iOS. Radar can't filter iOS out directly, so each day's iOS traffic is subtracted from the all-platform figures using Radar's iOS-only browser breakdown and iOS share of requests.

Brave is excluded. Brave sends Chrome's User-Agent string and names itself only in the Sec-CH-UA client hint. Radar reports it at about 0.002% of Chromium usage, roughly a thousand times below Brave's real size, so Brave's usage is unknown and is most likely counted as Chrome. brave.com therefore gets no usage share or value ratio. If Brave's real share was moved out of Chrome, Google's usage share would be a few points lower and its value ratio slightly higher.

Note on ChromeDerivative. Radar's bucket for Chromium-based browsers it can't name jumped from about 0.3% to about 10% of Chromium usage starting in 2026-W37 (on 9 September 2026). It came from every browser in proportion, Safari and Firefox included, not mostly from Chrome. It looks like Radar started labeling traffic it previously couldn't identify, possibly real Chromium-based browsers; Cloudflare hasn't explained it. Until that is explained, the value ratio and the table's usage shares leave the bucket out: each organization's usage share is its share of the other Chromium usage. This chart still shows the bucket.

    Placing comments on a file. Gerrit doesn't give us each CL's file list, so an inline comment counts for its own file. A patchset-level comment (the summary a reviewer writes when replying) counts for the file that the same reviewer commented on most in that CL. If that reviewer left no inline comment on the CL, the comment can't be placed: it shows as (no file) above and is left out of the other charts. Accounts that have never left an inline comment are left out entirely.

    Why only review tied to source files. Comments that can't be placed are mostly sign-offs, not review that can be weighed: in a sample, 39% of those on CLs with no inline comments were just “LGTM”, “thanks” or similar, against 2% of inline comments. Reading a sample of patchset-level comments from reviewers with no inline comment on the CL found mostly approvals, OWNERS sign-offs for one directory (“mojom lgtm”) and requests to route the CL elsewhere, and much of the spam posted to Gerrit. A reviewer who digs into the code usually comments on a line of it, so review attached to source files is the better measure of real investment. Leaving these comments out barely changes any organization's share of comments.
