Chromium Open Source - Value Exchange

One way to judge the health and stability of an open source project is to look at the relationship between each stakeholder's investment in it and the value it gets out of it. When that value exchange is far out of balance, it can lead to a rupture in the project community. Quantifying this value exchange is generally very difficult, but Chromium makes an approximation possible:

  • The value a browser gets from its engine is roughly proportional to that browser's usage.
  • Today, a primary cost of maintaining a large open source project is the effort of directing how the codebase evolves. AI coding agents have made code cheap to write, which makes deciding what should and shouldn't land in the project even more valuable. Code review that shapes what lands is therefore a reasonable proxy for an organization's investment in a large open source project.

This page approximates that value exchange in the Chromium project by comparing each organization's share of Chromium-based browser usage (according to Cloudflare Radar) with its share of addressed review comments: comments in review threads that led the change's author to modify the change. Other review stats are provided, but we focus on reviews which cause change as the subset which are most likely to be valuable to the project.

The Chromium repository is roughly split into infrastructure/engine code shared by every Chromium-based browser, and Google Chrome product code (e.g. Chrome UI). Chrome product code is reviewed almost entirely by Google for Google's own product. While much of this code is still valuable to others, we exclude it from this analysis since others cannot reasonably contribute review value under it.

This analysis should be treated as a rough approximation only, with trends over time likely more meaningful than absolute values at any point in time.

Review by organization

Scale

What's counted. Review comments on chromium/src CLs targeting main, each in the week it was written:

  • on merged, abandoned and still-open CLs (review that stops a CL landing counts too);
  • only on human-owned CLs, so autorolls and other bot CLs are left out;
  • not from bot or AI-agent accounts, nor owners on their own CLs (a reviewer's AI-assisted comments count as theirs);
  • only on the paths listed under Review by directory.

Votes with no comment, such as a bare +1, don't count: they don't show how much review went into them.

Metrics.

  • Addressed comments (the primary metric): comments in a thread that led the owner to change the CL, as explained under How review threads are classified. Weeks not yet classified show only the other metrics.
  • Review comments: every published comment, inline or patchset-level, including self-declared AI and post-merge ones (the table counts both).
  • Review characters: the length of those comments, without quoted (>) lines.
  • Reviewed CLs: CLs someone from the organization commented on, counted in the week the CL closed.

Organization. Each reviewer's organization as of the comment's date (for reviewed CLs, the close date), by the first rule that applies:

  1. their affiliation in Chromium's affiliations.json5, which credits @chromium.org and personal addresses to employers and follows job changes;
  2. other @chromium.org accounts count as google.com;
  3. otherwise their email domain (fb.com counts as meta.com).

Chromium browser usage (Cloudflare Radar)

The ratio's denominator: each browser's weekly share of Chromium-based browser usage (human traffic, complete weeks).

Left out of usage shares. This chart shows them, but the value ratio and the table don't, so each organization's share is of the remaining Chromium usage:

  • Android System WebView (ChromeMobileWebview): embedded by many browsers and apps, so it can't be credited to one organization.
  • ChromeDerivative, Radar's bucket for Chromium browsers it can't name. It jumped from about 0.3% to about 10% of Chromium usage on 9 September 2026, taken from every browser in proportion (Safari and Firefox too), which looks like a labelling change at Radar. Cloudflare hasn't explained it.

In-app browsers. Facebook and Instagram count for Meta, Microsoft 365 for Microsoft. Others (Snapchat, Pinterest…) stay in the total but count for no organization.

iOS is excluded, since every iOS browser must use WebKit. Radar can't filter it out, so each day's iOS traffic is subtracted using Radar's iOS-only browser breakdown and iOS share of requests.

Brave's usage is unknown. Brave sends Chrome's User-Agent and names itself only in the Sec-CH-UA client hint, so Radar reports it at about 0.002% of Chromium usage, roughly a thousand times too low; the rest is most likely counted as Chrome. brave.com gets no usage share or ratio. With Brave's real share moved out of Chrome, Google's usage share would be a few points lower and its ratio slightly higher.

How review threads are classified

    A thread is a reviewer's comment and every reply to it. It is addressed if the feedback led the owner to change the CL: code, tests, code comments, build files or the commit message.

    • Addressed: adopting all or part of a suggestion, a different change because of it, a TODO, moving code out of the CL, or agreeing to make the change (“I'll rephrase this”).
    • Not addressed: the owner answered, explained or pushed back; the comment was an approval, thanks or FYI; the work went to another CL or a bug; or the reply was a bare “Acknowledged”. This isn't bad review (questions are part of good review), just review that didn't change the code.

    How it's decided, first rule that applies:

    1. The owner started the thread or never replied: not addressed.
    2. The owner's first reply starts with “Done”, “Fixed”, “Fix applied.” or similar: addressed.
    3. Otherwise Claude Haiku reads the whole thread and decides.

    Scoring. Every comment in an addressed thread that isn't the owner's, up to the owner's last reply, earns its author one point, so back-and-forth and a second reviewer joining in earn more.

    Accuracy. Checked on 800 random threads with an owner reply (10 Aug – 1 Nov 2026), labelled blind by Claude Opus with disagreements settled by hand. The regex plus Haiku has a precision of 0.98 (98% of threads it counts as addressed were) and a recall of 0.99 (it finds 99% of addressed threads), each within about ±1 point. The regex settles 60% of threads (precision 0.98); Haiku the rest (precision 0.97, recall 0.96). 4 threads too unclear to call were left out. These are per-thread figures; points are per comment, so long threads weigh more. Details: docs/comment-classifier.md.

      Placing comments on a file. Gerrit doesn't give us each CL's file list, so:

      • an inline comment counts for its own file;
      • a patchset-level comment (a reviewer's reply summary) counts for the file that reviewer commented on most in the CL;
      • if the reviewer left no inline comment on the CL, it shows as (no file) above and is left out of the other charts. Accounts that have never left an inline comment are left out entirely.

      Unplaced comments are mostly sign-offs, not review: in a sample, 39% of those on CLs with no inline comments were just “LGTM”, “thanks” or similar (against 2% of inline comments), and most of the rest were OWNERS sign-offs (“mojom lgtm”), requests to route the CL elsewhere, or spam. Leaving them out barely changes any organization's share.
