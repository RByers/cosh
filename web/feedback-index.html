Chromium Open Source Health - Feedback Index

How much code review feedback Chromium contributors receive as they gain experience, and how yours compares.

This analysis is imperfect and is intended as a learning guide only. Please report any issues.

#

Feedback rate

One of the primary reasons a complex open source project like Chromium relies on code review is as a tool for learning, to help newer contributors learn the engineering practices of the community. When the project is healthy, contributors learn from their reviewers, reducing the need for their review and ultimately becoming reviewers themselves to help teach the next generation of contributors.

Feedback rate: addressed review comments per 100 lines written. That is the reviewer comment threads that led to a change in the code, for every 100 new or changed lines, over the changes someone landed. Removed lines don't count, since they draw almost no feedback. Large-scale changes and other large mechanical changes are left out.

      #

      Feedback index

      Feedback index: a contributor's feedback rate compared with their peers'. The peers' rate is the median rate of contributors with the same experience (the line in the chart above), adjusted for how much feedback per line the directories they worked in draw. 1.00× is typical; below 1 means less feedback than peers, above 1 more. Because it compares each change with others at the same experience, the index doesn't fall as someone gains experience the way the rate does: it shows how someone's feedback compares with their peers' at every stage.

            By organization

            The median contributor's feedback rate over their changes whose main directory (two levels) is in each directory, and over their changes from each organization, for the directories and organizations with the most contributors ( or more changes each). Directories matter much less than experience or size, except that imported third-party code and configuration directories (such as third_party/libvpx/ or testing/buildbot/) draw almost no feedback per line. Organizations differ, but mostly through their contributors' experience. The feedback index adjusts for directories by default, and for organization if you choose it.

            How it's measured

            Changes are the merged, human-owned Chromium changes on main that landed from to , leaving out mechanical ones (100 or more files, or mostly repeated lines) and large-scale changes (CLs whose commit message cites Chromium's LSC process, or that git cl split uploaded), as on the Review Balance page. A review comment is a comment thread on Gerrit started by someone other than the change's owner, bots left out, on a file or the commit message (general comments on the whole change aren't counted: they can't be tied to a directory, and few lead to a change in the code). It is addressed when the owner's reply led to a change in the code, as judged by a regular expression for “Done”-style replies and by an AI model (Claude Haiku) for the rest (how). Lines are the new or changed lines (Gerrit's insertions); removed lines don't count, because they draw almost no feedback, and changes that only remove lines are left out.

            A feedback rate is pooled: all the addressed comments on a set of changes per 100 of all their lines. Experience is the number of CLs the owner had landed on main, counting the change itself (their commits since 2008, reverts left out), in bins that double: 8 or fewer, 9–16, 17–32 and so on up to 2k and more. A contributor's rate in a bin counts with or more changes there.

            The feedback index divides the addressed comments on your changes by the number your peers would have drawn on the same lines: for each change, its lines times the median rate of the opening chart at your experience then, times a factor for each directory it changed (by how much more or less feedback per line the directory draws than its changes' experience predicts), and, if chosen, a factor for your organization. Directories with fewer than 300 changes take their top-level directory's factor (or none), and smaller organizations share one factor. The factors are scaled so that the median contributor's index doesn't change by adding them. Without experience, the typical rate is the median of everyone with or more changes. The spread of everyone's index (the tiles and the over-time chart) counts contributors with or more changes in the period.

            Addresses are matched as in the Review Balance page: chromium.org and google.com addresses with the same name are one person, and so is a Gerrit owner with the git author of the same changes. The data has one file per person, named by a one-way hash of their address, so this page can only find someone whose address you already know. Everything comes from public Gerrit and git data. Code and method: docs/review-feedback.md.
