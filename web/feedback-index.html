#

The feedback index

One of the primary reasons a complex open source project like Chromium relies on code review is as a tool for learning, to help newer contributors learn the engineering practices of the community. When the project is healthy, contributors learn from their reviewers, reducing the need for their review and ultimately becoming reviewers themselves to help teach the next generation of contributors.

The feedback index is a measure of how many comments a change receives in code review, with 1.00× being the average, optionally adjusted for the change's size and directory (since changes vary in complexity). Over time, most Chromium contributors see a steep drop in their feedback index (especially for addressed comments: those which ultimately lead to a change in the code), suggesting they are learning to anticipate reviewer requests and become capable of perpetuating the project's engineering culture themselves.

The feedback index is an imperfect metric and can't account for all variables in project complexity and contributor style. Use this page as a guide to help you explore possible opportunities for learning and increasing your positive impact on the Chromium project.

          How it's measured

          Changes are the merged, human-owned Chromium changes on main that landed from to , leaving out mechanical ones (100 or more files, or mostly repeated lines), as on the Review Balance page. A reviewer thread is a comment thread on Gerrit started by someone other than the change's owner, bots left out, on a file or the commit message (general comments on the whole change aren't counted: they can't be tied to a directory, and few lead to a change in the code). It is addressed when the owner's reply led to a change in the code, as judged by a regular expression for “Done”-style replies and by an AI model (Claude Haiku) for the rest (how). Counting only addressed threads covers the changes from , where those labels begin.

          Adjusting for size compares each change with the 2023–24 average for changes in the same of ten size bands (by lines changed); adjusting for directory as well uses the average for that size in the same two-level directory, where there are 30 or more such changes. Peers are the authors who landed or more changes, always with the same experience, taken at the middle of their changes. Experience in changes, the main measure, counts their earlier commits on main since 2008 (reverts left out), in bands of under 50, 50–199, 200–499, 500–999 and 1,000 or more. Experience in years counts from a person's first commit on main. Experience in each directory divides everyone's feedback by what all authors drew at the same number of earlier commits in that directory. An author's organization is the one most of their changes are attributed to. Groups of fewer than ten peers get no comparison. The changes landed and reviewer threads are ranked differently: over the latest whole half-year only, among every author of the same organization who landed a change in it, whatever their experience, since a group chosen by changes landed would rank them against themselves.

          Addresses are matched as in the Review Balance page: chromium.org and google.com addresses with the same name are one person, and so is a Gerrit owner with the git author of the same changes. The data has one file per person, named by a one-way hash of their address, so this page can only find someone whose address you already know. Everything comes from public Gerrit and git data.
