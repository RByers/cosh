# Chromium Gerrit API research for review-activity extraction

Status: research only. No extraction code has been written yet.
Date of probes: 2026-11-03. All probes were anonymous.

Probe helper scripts are in `.research/gerrit/scripts/`. Raw responses are in
`.research/gerrit/responses/`, which also holds `_requests.log`, one line per live
request. Treat those responses as untrusted data.

**Probe budget used:** 37 live requests to googlesource hosts:
- 32 REST GETs.
- 1 `git ls-remote`.
- 4 `git fetch` attempts. One returned nothing, so 3 git fetches succeeded.

Requests were serial, sent with `--compressed`, and spaced at least 1.5 s apart. Pages with
`n=500` were used only for the volume count.

Each statement below carries one of two labels:
- **[verified]**: observed in a live probe.
- **[docs]** or **[inferred]**: taken from documentation or source code, or reasoned out.

---

## TL;DR: recommended approach

1. **Enumerate CLs:** for each **UTC day**, query:
   ```
   GET https://chromium-review.googlesource.com/changes/?q=project:chromium/src+status:merged+mergedafter:"D 00:00:00 +0000"+mergedbefore:"D+1 00:00:00 +0000"&o=DETAILED_ACCOUNTS&o=DETAILED_LABELS&n=500&S=0,500,1000
   ```
   - Assign each CL to the **submitted** timestamp, not `updated`.
   - Deduplicate on `_number`, because both bounds are inclusive.
   - A weekday has about 1,300–1,500 merged CLs, so 3 pages per day. That is about 16–20 listing requests per week.
2. **Fetch comments:** for each CL whose owner is not a `SERVICE_USER` and whose
   `total_comment_count > 0`, call `GET /changes/chromium%2Fsrc~{N}/comments`. That is about
   **4,000 requests per week**.
3. **Build a row:** one row per (CL, reviewer), where the reviewer is not the CL owner and is
   not a service user.
   - Count `/comments` entries authored by the reviewer, including `/PATCHSET_LEVEL` entries.
     Exclude entries with `is_ai: true` or a `tag` starting with `autogenerated:`.
   - Characters = sum of `len(message)`.
   - The review/vote bit comes from `labels.Code-Review.all[].value > 0`.
   - Emails come directly from `DETAILED_ACCOUNTS`.
4. **OWNER bit: defer it.** The code-owners REST API computes against the **current** OWNERS
   files, not the ones in force at review time [verified]. So it is wrong for a backfill. For
   history, compute ownership from OWNERS files at the merge commit's parent (see §4).
5. **Five-year backfill:** prefer **batched `git fetch` of NoteDb `refs/changes/*/*/meta`
   refs**, which can be fetched anonymously [verified].
   - Use the REST listing to get the CL list and the account-ID-to-email map.
   - Fetch 200–500 meta refs per git request. That is about 13k git fetches plus about 5k listing
     requests in total, compared with about 1M REST `/comments` calls.
6. **Rate:**
   - Serial: 1 request at a time, at least 1 s gap.
   - gzip on.
   - Strip the 5-byte `)]}'\n` prefix from responses.
   - Back off exponentially on HTTP 429.
   - One week by REST: about 4,050 requests, roughly **1.5–2 h** wall-clock.

## 1. Enumerating CLs in a time window

### Query syntax

- `project:chromium/src status:merged mergedafter:"2026-10-27 00:00:00 +0000" mergedbefore:"2026-10-28 00:00:00 +0000"` works [verified].
  - URL-encode the quotes, spaces and `+` as `%22`, `+` and `%2B`.
- According to the docs, both `mergedafter` and `mergedbefore` are **inclusive**, and the timezone defaults to UTC [docs, user-search.html]. Pass `+0000` explicitly anyway.
- **Use the submitted time (`mergedafter`/`mergedbefore`), not `after:`/`before:`.** `after:`/`before:` filter on `updated`, and `updated` keeps changing after merge [verified]. Examples:
  - CL 8648715 was submitted on 2026-10-26 and has `updated` 2026-11-02, because someone left a comment after the merge.
  - The `removed_from_attention_set` and hashtag edits that appear in the probe responses also change `updated` [inferred].
  - Windows based on `updated` would therefore count the same CL again in later windows.
- `branch:main` restricts results to trunk. On 2026-10-27, 121 of 1,318 merged CLs were on release or other branches, mostly cherry-picks by bots and humans [verified].
- Only merged CLs are counted. Review effort on **abandoned** CLs is lost (see open questions). An `abandoned` window would need a different date field, because there is no `abandonedafter`; `before:`/`after:` on `updated` is the closest [docs].

### Paging

- **The maximum page size for anonymous callers is 500.** A request with `n=1000` returned 500 results with `_more_changes: true` [verified].
- `_more_changes: true` appears on the **last element** of the array when another page exists [verified].
- `S=<offset>` (or `start=`) pages through results [verified].
- **Deep offsets are slow.** Page time grew from about 1 s at `S=0` to 7–9 s at `S=2000–4000` [verified, `_requests.log`].
- **Results are sorted by `updated` descending, not by submit time** [verified]. A CL updated during paging can therefore shift between pages.
- Mitigations:
  - Keep windows small: one UTC day is 3 pages or fewer.
  - Deduplicate on `_number`.
  - Re-run a window if the count looks off.
  - Optionally re-query a window later to catch stragglers.

### Response weight by `o=` option

These measurements come from the same 3-CL query [verified]:

| Options | Raw bytes/CL | gzip bytes/CL | Notes |
|---|---|---|---|
| (none) | ~1.3 KB | ~350 B | includes `owner._account_id`, `submitter`, `submitted`, `total_comment_count`, `unresolved_comment_count`, insertions/deletions |
| `DETAILED_ACCOUNTS` | ~4.8 KB | ~350–630 B | adds `email`, `name`, `tags` (e.g. `SERVICE_USER`), avatars for owner/submitter |
| `+MESSAGES` | ~56 KB | ~4.4 KB | dominated by LUCI CQ dry-run boilerplate |
| `+DETAILED_LABELS +SUBMIT_REQUIREMENTS` | ~96 KB | ~7.2 KB | adds `reviewers{REVIEWER,CC}` and `labels.*.all[]` per-voter values |

- In a 25-CL sample with `DETAILED_ACCOUNTS+MESSAGES+DETAILED_LABELS`, the response was 2.1 MB raw and 133 KB gzip, about 5.3 KB gzip per CL [verified].
- `reviewers` (with REVIEWER and CC buckets) is returned together with `DETAILED_LABELS` [verified].
- `ALL_REVISIONS`, `ALL_FILES` and `CURRENT_FILES` are not needed. Leave them out, because they are heavy [docs].
- **Recommendation:** use `o=DETAILED_ACCOUNTS&o=DETAILED_LABELS`.
  - Add `o=MESSAGES` only if you want vote and reply events with timestamps (see §3).
  - With `MESSAGES` included, use `n=100` to keep each response at a few MB or less.

## 2. Attributing reviews to email addresses

- **Anonymous callers can see emails** on chromium-review [verified]. With `DETAILED_ACCOUNTS`, `owner`, `submitter`, `reviewers.REVIEWER[]`, `reviewers.CC[]`, `labels.*.all[]` and `messages[].author` all include `email`.
  - Example: `{"_account_id":1234567,"name":"<name>","email":"<user>@gmail.com"}`.
- `GET /accounts/{id}/detail` also works anonymously and returns `email` and `registered_on` [verified].
  - `{"registered_on":"2011-04-27 17:13:26","_account_id":1000169,"name":"<name>","email":"<user>@chromium.org"}`
- **Accounts without an email** are possible. One example was `gwsq` (`_account_id 1255833`), which returned only `name` and `tags:["SERVICE_USER"]` [verified]. In the 25-CL sample, this was the only reviewer with no email.
  - Fallback: key the row on `_account_id`, with `email = NULL`.
- **Email-only reviewers or CCs** are entries with `_account_id: null` and an email, such as `webapks-watchlist@chromium.org` or `<user>+watch@chromium.org` [verified]. These are watchlists or unregistered addresses and never review. Drop them.
- **Bots:** `DETAILED_ACCOUNTS` puts `"tags":["SERVICE_USER"]` on service accounts [verified]. Examples:
  - `chromium-scoped@luci-project-accounts.iam.gserviceaccount.com` (LUCI CQ)
  - `chromium-autoroll@skia-public.iam.gserviceaccount.com`
  - `blink-w3c-test-autoroller@chromium.org`
  - `rubber-stamper@appspot.gserviceaccount.com`
  - `crash@system.gserviceaccount.com`
  - `gwsq`

  In the samples, every bot found by matching email domain or name also carried `SERVICE_USER`. Use the tag as the primary filter and an email-regex denylist as a backstop.
- **Roles:**
  - The CL author is `owner`. The uploader can differ, and `submitter` is usually LUCI CQ.
  - Reviewers are in `reviewers.REVIEWER`, CCs in `reviewers.CC`.
  - The code-owners plugin auto-adds people, and LUCI CQ appears as a REVIEWER on most CLs [verified].
- **Suggested definition of "a review" by person P on CL C:**
  - P ≠ owner, P is not a service user, and P did at least one of:
    - (a) cast a Code-Review vote of +1 or −1. In chromium/src, Code-Review max is +1; `permitted_voting_range {min:1,max:1}`.
    - (b) authored at least one published `/comments` entry, inline or `/PATCHSET_LEVEL`.
  - Being merely in REVIEWER or CC is not a review. A CC who comments counts.
  - `labels.Code-Review.all[].date` on merged CLs showed the **submit time**, not the original vote time [verified, CL 8648715]. Get real vote times from `messages` or NoteDb.
- **Organization:** take the domain of `email`. Owners on 2026-10-27, excluding bots, were mostly from these domains [verified]:

  | Domain | CLs |
  |---|---|
  | chromium.org | 494 |
  | google.com | 399 |
  | microsoft.com | 23 |
  | igalia.com | 12 |
  | samsung.com | 10 |
  | gmail.com | 8 |
  | intel.com | 3 |

  - Many Googlers use `@chromium.org` addresses, so domain alone understates Google. This is a known limitation, not something to solve now.

## 3. Counting review comments and characters

### Change messages: o=MESSAGES and NoteDb

- In modern Gerrit, top-level change messages are **almost entirely boilerplate** [verified]. Examples:
  - `"Patch Set 2: Code-Review+1"`
  - `"Patch Set 4:\n\n(5 comments)"`
- In the 25-CL sample, removing `^Patch Set N:.*$` and `^\(N comments?\)$` left **no human text** [verified].
- The text a reviewer types into the reply box is stored as a **`/PATCHSET_LEVEL` comment**, which you get from `/comments`, not from the message [verified]. Example: `{"f":"/PATCHSET_LEVEL","a":"<reviewer>@chromium.org","msg":"PTAL <name>"}`.
- **Message `tag` values seen** [verified]:

  | Tag | Count |
  |---|---|
  | `autogenerated:cq:dry-run[:<ts>]` | 359 |
  | `autogenerated:gerrit:newPatchSet` | 143 |
  | `cq:full-run` | 40 |
  | `newWipPatchSet` | 38 |
  | `gerrit:code-owners:addReviewer` | 25 |
  | `gerrit:merged` | 25 |
  | `autogenerated:plugin` | 17 |
  | `setHashtag` | 11 |
  | `autogenerated:jetski-code-review` | 1 |
  | `autogenerated:review-nudge` | 1 |
  | `slsa-policy-verified` | 1 |
  | `luci-cv:trigger-dep-cl` | 1 |

  Human replies have `tag: null`.
- Rule: drop any message whose tag starts with `autogenerated:`.
  - `autogenerated:jetski-code-review` is an **LLM "Early Review" posted under a human's account** (a named reviewer) [verified].
  - `autogenerated:plugin` messages are UI-plugin votes (Commit-Queue+1).
- Messages are useful only for **vote events with timestamps** and for detecting "replied without comments", which is rare. Recommendation: skip `MESSAGES` in the main pass.

### Inline comments: `/changes/{id}/comments`

```
GET https://chromium-review.googlesource.com/changes/chromium%2Fsrc~8622067/comments
```

- Returns only **published** comments; drafts are private. The result is a map keyed by file path, including `/COMMIT_MSG` and `/PATCHSET_LEVEL` [verified].
- Fields [verified]: `author{_account_id,name,email,…}`, `id`, `in_reply_to`, `patch_set`, `line`, `range`, `message`, `unresolved`, `updated`, `change_message_id`, `commit_id`, plus:
  - **`is_ai: true`**: an AI-generated comment posted by a human reviewer. CL 8562008 had 2 comments by a reviewer with `is_ai:true`.
  - `tag`, when set. The NoteDb batch showed `autogenerated:gerrit-mcp`.
- **AI comments are already significant.** In a 50-CL NoteDb sample, 48 of 351 comments (14%) had `isAi=true`, and most of those had **no tag** [verified]. Filter on `is_ai`, not on tags alone.
- `total_comment_count` from the listing matched the `/comments` count (18 = 18 for CL 8622067) [verified]. Use it to skip CLs with zero comments: 28% of human CLs on 2026-10-27 had none.
- **Post-merge comments exist.** CL 8648715 got a comment one week after merge [verified]. Decide whether to keep only comments with `updated <= submitted`. I'd keep all comments and record the timestamp.
- Gotchas:
  - Some "human" comments are forwarded analyzer output, e.g. `"Please fix this WARNING reported by ClangTidy: …"` posted by a reviewer [verified]. Optionally discount text that matches known analyzer templates.
  - Replies quote earlier text with `> ` lines. Strip those before counting characters [inferred].
- **Bulk across CLs:** the REST API offers **no** multi-change comments endpoint and no `o=` option that inlines comments into `/changes/?q=` [docs]. REST therefore needs one request per CL. The bulk alternative is NoteDb via git (§5).

## 4. OWNER bit

- **`GET /changes/{id}/code_owners.status` works anonymously** [verified]:
  - About 0.2–0.6 s, under 1 KB gzip.
  - Per-file `status` (`APPROVED`, `INSUFFICIENT_REVIEWERS`, `PENDING`, …) and `reasons`, e.g. `"approved by <GERRIT_ACCOUNT_1000169> who is a code owner"`, plus an `accounts` map from ID to email.
- `GET /changes/{id}/revisions/current/owned_paths?user=<email>` also works anonymously [verified]. It took 2.25 s and covers one user per call.
- **Neither endpoint is historical.** The plugin reads OWNERS from the **current tip of the destination branch** [docs: `CodeOwnerApprovalCheck.getDestBranchRevision` returns "the current revision of the destination branch"; the Suggest endpoint says "tip of the change's destination branch"].
  - Confirmed on 2021 CL 3245532: today it reports `chrome/browser/ui/hats/trust_safety_sentiment_service_browsertest.cc` as `INSUFFICIENT_REVIEWERS`, even though the CL merged with the Code-Owners requirement satisfied [verified].
  - Reviewer `<user>@google.com` voted CR+1 but is not named as an approver of any file now [verified].
- `code_owners.check` (branch-level) needs the "Check Code Owner" capability for `user=` [docs]. It was not probed; authenticated endpoints were off-limits.
- **Historical signals in the data** [verified]:
  - `autogenerated:gerrit:code-owners:addReviewer` messages: "`<ACCOUNT>`, who was added as reviewer owns the following files: …". These are written at the time a reviewer is added, but only for some adds.
  - `Owners-Override+1` votes, with the message "the code-owners submit requirement is overridden by …".
  - NoteDb `Submitted-with: Rule-Name: Code-Owners` + `OK`. This is CL-level only and names no person.
  - Chromium does **not** post "files are now code-owner approved by X" messages.
- **Recommendation: defer.**
  - For the first week, optionally call `code_owners.status` once per human CL (about 5.5k requests per week). Current OWNERS files are a good approximation for a recent week. Record `owner_bit_source = 'code_owners.status@<date>'`.
  - For the backfill, compute ownership offline:
    - Keep a local partial clone of `chromium/src` with only OWNERS blobs, using `--filter=blob:none` plus sparse fetch of OWNERS files.
    - Evaluate Chromium OWNERS semantics at the **parent of the merge commit**: `set noparent`, `per-file`, `file://` includes, and `*`.
    - Check the result against each reviewer and the CL's file list. The file list needs `o=CURRENT_FILES` or `/revisions/current/files`, one more request per CL.

    This needs no Gerrit calls beyond file lists, and it is historical.

## 5. Load minimization and bulk alternatives

- **Etiquette and quotas:** I found no published per-IP rate limit for anonymous `*.googlesource.com` REST [searched].
  - Googlesource returns **HTTP 429** under throttling. A chromium-dev thread from April 2026 reports 429s from chromium.googlesource.com even for single `ls-remote` calls during an incident (https://groups.google.com/a/chromium.org/g/chromium-dev/c/ZUQuUJDd8HM).
  - No rate-limit headers are returned. Only `x-gerrit-trace` was seen [verified].
  - Authenticated callers (`.gitcookies`) are commonly understood to get higher quotas [inferred], but auth was out of scope.
- **Practice:**
  - Serial requests, at least 1 s gap.
  - `Accept-Encoding: gzip`, which the server honors (`content-encoding: gzip`) [verified].
  - Identify yourself with a User-Agent.
  - Exponential backoff on 429 or 5xx.
  - Avoid deep `S=` offsets.
  - Cache everything immutable: merged CLs rarely change.
  - Run during US night if possible.
- **XSSI prefix:** every JSON body starts with `)]}'\n` (5 bytes) [verified]. Strip it before parsing.
- **BigQuery or exports:** no official public BigQuery dataset of Chromium Gerrit was found [searched].
  - The academic "Chromium Conversations Corpus" (Cornell ConvoKit, 2.8M comments) is a dated research snapshot. It is not suitable for ongoing 5-year organization-level counts.
  - A 2025 chromium-dev request for "all changes" had no answer.
- **NoteDb meta refs over git: works anonymously** [verified].
  - `git ls-remote https://chromium.googlesource.com/chromium/src 'refs/changes/67/8622067/*'` lists `refs/changes/67/8622067/meta`.
  - The ref path is `refs/changes/<last-2-digits>/<N>/meta`.
  - `git fetch <url> refs/changes/67/8622067/meta:refs/meta/8622067` works. It produced a 35-commit history.
  - **Contents:**
    - One commit per event, with a body and footers: `Patch-set`, `Label: Code-Review=+1, <uuid> Gerrit User 1000169 <1000169@<serverId>>`, `Reviewer:`, `CC:`, `Tag:`, `Real-user:`, `Attention:`, `Status: merged`, `Submitted-with:`, and so on.
    - The tree holds **notes blobs keyed by revision SHA** with a JSON `comments[]` array. Fields: `key{uuid,filename,patchSetId}`, `author{id}`, `writtenOn`, `message`, `unresolved`, `parentUuid`, `tag`, `isAi`, …
  - For CL 8622067 the count matched REST exactly: 18 comments.
  - **Identities are numeric account IDs only, with no emails.** Resolve them with the `DETAILED_ACCOUNTS` data from the REST listing, which covers owner, reviewers, CCs and voters, or with a cached `/accounts/{id}` lookup for leftovers.
  - **Batching works:** one `git fetch` can take many refspecs [verified].
    - 50 refs gave a 769 KiB pack.
    - 200 refs gave a 3.25 MiB pack in **45 s** wall-clock, about 0.22 s and 17 KB per CL.
    - A refspec glob for all of `refs/changes/*` would advertise millions of refs. Don't do that; list CLs via REST and fetch explicit refspecs.
  - Server work per CL is similar to REST `/comments` (about 0.22 s compared with 0.23 s per request), but it needs **about 200–500 times fewer HTTP requests**, and it also returns the full vote, reviewer and CC history with real timestamps.
  - NoteDb is an internal storage format. Its footer formats can change, so parse defensively.

### Request estimates

These assume about 7,600 merged CLs per week, about 5,500 of them human-owned, and about 4,000 human CLs with at least one comment.

| Approach | 1 week | 5 years (~260 wk, assuming similar volume) | Wall-clock at polite serial rate |
|---|---|---|---|
| A. REST listing (3 pages/day) + `/comments` per commented human CL | ~20 + ~4,000 ≈ **4,050 req** | ~1.05M req | ~1.5–2 h/week; **~13–15 days** for 5 years at 1 req/s |
| A + `code_owners.status` per human CL (current-OWNERS approximation) | +5,500 | n/a: not historical | +1.5–2 h/week |
| B. REST listing + NoteDb `git fetch` in batches of 200 human CLs | ~20 + ~28 fetches | ~5k listing + ~7k fetches (about 1.4M human CLs, some weeks smaller) | about 0.22 s/CL of server time, ≈ **20 min/week; ~3.5 days** for 5 years serial. About 17 KB/CL, so roughly 25 GB of packs |

**Recommendation:**
- Build the pipeline and data model on approach A for the first week. It is simplest, includes emails and `is_ai`, and uses documented APIs.
- Use approach B for the backfill, cross-checked against A on that first week.
- Older years probably had lower volume, so 5-year totals are upper-bound-ish [inferred]. Measure one older week before committing.

## Open questions

1. Should reviews on **abandoned** or still-open CLs count? A merged-only window misses them. Including them needs an `updated`-window plus dedupe, or a periodic re-scan.
2. Should comments posted after merge count, and should self-replies by the CL owner be excluded? I recommend yes to the exclusion.
3. How should `is_ai` comments be treated: excluded, or counted separately? How about human comments that forward ClangTidy or analyzer findings?
4. Which branches count: `main` only, or also release-branch cherry-picks? Those are mostly bot-owned or rubber-stamped.
5. What is the actual anonymous 429 threshold? It is unknown, so ramp up slowly and monitor. Should we ask Chromium infra (infra-dev@chromium.org) before a 5-year backfill, especially for the NoteDb git approach?
6. Historical OWNERS evaluation needs a faithful implementation of Chromium OWNERS semantics. How much effort is that worth versus keeping the bit as current-only?
7. Should orgs be resolved beyond email domain, since many Googlers use @chromium.org?

## Verified vs. inferred: summary

- **Verified live:**
  - Anonymous emails and `SERVICE_USER` tags.
  - Page cap of 500, `_more_changes`, and sort by `updated`.
  - Slow deep `S=` offsets.
  - Option sizes.
  - `updated` drifting after merge.
  - `/comments` fields including `is_ai` and `/PATCHSET_LEVEL`.
  - Messages being boilerplate.
  - The jetski LLM review tag.
  - `code_owners.status` and `owned_paths` working anonymously and being non-historical (2021 CL).
  - NoteDb meta refs fetchable anonymously, batched, and matching REST counts.
  - Daily volumes.
