# Cloudflare R2: published files too big for git

Some published data is too big or changes too often for git, so the site
fetches it from the Cloudflare R2 bucket `cosh`, served at
**https://cosh-data.rbyers.ca/** (docs/plan.md, 2026-11-14).
`config/r2.json` lists each prefix and the folder under `data/private/` it
is uploaded from:

| Prefix | Local folder | What | Written by |
|---|---|---|---|
| `review-feedback/threads/v2/` | `review-threads/` | The Feedback Index's comment download, `<half-year>/<name>.json` (docs/review-feedback.md, "Downloading your comments") | `cosh.review_threads` |
| `review-feedback/people/v2/` | `feedback-people/` | The Feedback Index's per-person files, `<name>.json`, one per person | `cosh.review_feedback` |
| `review-load/people/v2/` | `review-load-people/` | Review Load's per-reviewer files, `<name>.json`, one per reviewer | `cosh.review_load` |

`<name>` is the person's normalised address (`cosh.review_feedback.file_name`,
`personFile` in `web/src/feedback.ts`). Until 2026-11-14 the files were
named by a salted hash of it (`threads/`, `people/v1/`), which mattered
while they were committed to git, where anyone can list them; the bucket
can't be listed. That move also joined each person's small files into one:
a lookup was up to 20 requests of a few hundred bytes (Feedback Index) or
14 of about 100 bytes (Review Load), and is now one, and the bucket went
from 63,433 such objects to 12,100. The thread files stay one per
half-year: they are large, loaded one half-year at a time, and joining
them would make each weekly publish re-upload every active person's whole
history.

Each page's small global file (`peers.json`, `reviewers.json`, `all.json`)
stays in git: everyone loads it, and its diffs are worth reading. The
bucket is named for the project, not the page, so other analyses can use it
under their own prefix (add it to `config/r2.json` and
`config/dataflow.json`).

What goes in the bucket, and how it may change, is set by `docs/goals.md`,
goal 4: new data must not break pages already deployed (add rather than
change; a breaking schema change goes under a new name such as a version
prefix), and a weekly sync writes only the files that changed.

Everything in the bucket can be rebuilt from `data/private/` and uploaded
again, so losing it, or a bad upload, costs a rerun, not data.

Set up on 2026-11-14. Items marked *(confirm)* were done in the Cloudflare
dashboard and not seen from argus; check them there when you next look.

## What is where

| Thing | Where |
|---|---|
| Cloudflare account | The user's own, logged in only from the laptop (never argus) |
| Bucket | R2 → `cosh`, location automatic, Standard storage |
| Public address | Custom domain `cosh-data.rbyers.ca` on the bucket (Settings → Custom Domains) |
| Credentials on argus | `~/.secrets/cosh/r2.json` (mode 600): `endpoint`, `bucket`, `access_key_id`, `secret_access_key`, `public_base` |
| Prefixes and their local folders | `config/r2.json`, read by `cosh/r2.py`, the pages (`web/src/r2.ts`) and Vite (`web/vite.config.ts`) |
| Upload code | `cosh/r2.py` (`python3 -m cosh.r2 publish [prefix ...]`, or `sync <dir> <prefix>`), standard library only |
| What was uploaded | `data/private/r2-manifest.json`: object key → sha256, size and when its file was last seen at a publish |
| Past publishes | `data/private/r2-publishes.json`: each publish's start time and prefixes (the newest 100) |
| Object layout | `<prefix>/<path>`; a local `*.json.gz` becomes `*.json`, stored gzipped |

## Bucket settings

- **Public access:** only through the custom domain. The `r2.dev` URL was
  never turned on (keep it off: it is rate limited and can't take cache
  rules). Nothing lists the
  bucket publicly: an object is reachable only by its exact key, the
  person's address, so a person's files are found only by typing it
  (ground rule 5).
- **CORS policy** (Settings → CORS Policy), checked from argus on
  2026-11-14: `cosh.rbyers.ca` gets `Access-Control-Allow-Origin`, other
  origins get none, a preflight answers 204.

  ```json
  [
    {
      "AllowedOrigins": ["https://cosh.rbyers.ca", "http://localhost:5182"],
      "AllowedMethods": ["GET", "HEAD"],
      "AllowedHeaders": [],
      "MaxAgeSeconds": 86400
    }
  ]
  ```

  The origin is exactly the scheme and host, no trailing slash.
  `localhost:5182` is the preview build on argus (`npm run serve`). Local
  pages no longer read the bucket (see "Local copies on localhost"), so
  that origin can be dropped from the policy.
- **Object metadata** is set by `cosh.r2` on upload: `Content-Type`
  (`application/json` for `.json`), `Content-Encoding: gzip` for files
  uploaded from `.gz`, and `Cache-Control: public, max-age=86400`.
  Browsers unpack the gzip themselves.

## The domain (rbyers.ca, on Cloudflare since 2026-11-14)

R2 custom domains need the zone's DNS on Cloudflare, so rbyers.ca's
nameservers moved from Squarespace's (Google Cloud DNS) to
`eve.ns.cloudflare.com` and `nico.ns.cloudflare.com`. The domain is still
registered at Squarespace; only the nameservers changed. Moving the
registration too is optional (check first that Cloudflare takes `.ca`
transfers).

- The records were copied from what the old nameservers served (a zone file
  imported with proxying off) and checked afterwards over DNS-over-HTTPS:
  every CNAME and TXT matched. The GitHub Pages hosts (`cosh`, `cpu`, `lt`,
  `meshcore`, `ncov`, `razerweb`, `webkit`, `zpcr`) stay **DNS only**
  (grey cloud), so GitHub keeps issuing their certificates; so do the
  Cloudflare Pages hosts (`fitman`, `lab`), `home`/`argus` (Firewalla's
  dynamic DNS) and the Google verification record.
- Mail for rbyers.ca moved from Squarespace's forwarding (Mailgun) to
  Cloudflare Email Routing (its MX and SPF records). The old Mailgun DKIM
  record `k1._domainkey` was deleted.
- `rbyers.ca` and `www.rbyers.ca` redirect (302) to the Bluesky profile
  through Cloudflare, as the old host did.
- `cosh-data.rbyers.ca` is the bucket's custom domain (Cloudflare made the
  record; proxied).

## Caching and rate limits

- **Cache rule** on the zone for hostname `cosh-data.rbyers.ca`: eligible
  for cache, edge TTL from the origin's `Cache-Control`. Checked: the
  second fetch of an object is a `cf-cache-status: HIT`. Cached copies
  vary by `Origin`. Served from the cache, a download costs no R2 read.
- **New data reaches people within the day** at most, without purging: the
  page asks for `?v=<data end>` (`peers.end`), so each new week is a new
  cache key.
- **No rate-limiting rule** (decided 2026-11-14). Cached downloads cost
  nothing, and the budget alert catches abuse that gets past the cache. If
  one is ever needed: Security → WAF → Rate limiting rules on the
  hostname, about 100 requests per 10 s per IP (a download is 2 to 19
  requests).

## Costs and limits

R2 charges nothing for egress. Beyond the free tier (10 GB-month of
storage, 1M writes and 10M reads a month): about $0.015 per GB-month,
$4.50 per million writes, $0.36 per million reads. Cloudflare has no hard
spending cap for R2, only alerts.

- Use on 2026-11-14: about 440 MB (96,109 objects: 32,676 threads, 39,660
  Feedback Index and 23,773 Review Load files), so storage is free. The
  first uploads were one write per object. With the files named by
  address and joined per person (v2, 2026-11-14): about 435 MB in 44,776
  objects (32,676 threads, 6,984 Feedback Index and 5,116 Review Load
  files); twice that for the day both versions are in the bucket. A
  weekly publish writes the changed files only: the current half-year's
  threads and the per-person files of people with changes in it (about
  1,900 each, 18 MB of per-person files).
- **Budget alert** (Billing → Billable Usage) at about $5, e-mailed
  *(confirm)*. Anything above $0 means something is wrong.
- `cosh.r2 sync` refuses to write or delete more than 50,000 objects for
  one prefix in one run (`--max-objects`) or to leave more than 5 GB in the manifest
  (`--max-total-gb`). That catches our own bugs; it can't stop a
  compromised argus, which the budget alert covers.

## The token on argus

An **Account API token** (R2 → Manage API tokens) with **Object Read &
Write on the `cosh` bucket only**. It can't read or change bucket
settings (CORS, domains), other buckets, DNS or the account: a request
for the bucket's CORS policy with it gets 403. Client IP filtering
(argus's public IP) and an expiry *(confirm)*.

argus is assumed compromisable (argus-config SECURITY.md), so the token is
kept narrow and revocable:

- **What a stolen token can do:** overwrite, delete or add objects in
  `cosh`, so it could serve wrong data at `cosh-data.rbyers.ca`, wipe the
  bucket, or run up storage and write charges (the budget alert catches
  that). It can't touch the DNS, the site on GitHub Pages, or e-mail.
- **To revoke it:** on the laptop, R2 → Manage API tokens → the token →
  Delete (or roll it). To stop serving at once, also turn off the custom
  domain under the bucket's Settings → Custom Domains.
- **To rotate it:** create a new token with the same scope, write its
  values into `~/.secrets/cosh/r2.json` on argus with an editor (not
  `echo`, which leaves the secret in shell history), then delete the old
  token.
- The file stays out of `~/projects`, out of the repo and off command
  lines; `cosh.r2` reads it and never prints it. Never paste its values
  into a Claude session.

## Deploying: upload to R2, then push

**Deploying means two steps, in this order:**

1. **Upload to R2**, from the main checkout, and wait for it to finish:

   ```
   nice -n 5 python3 -m cosh.r2 publish [--dry-run]
   ```

2. **Push `main`** to GitHub, whose Pages workflow deploys the site.

Uploading is part of deploying and nothing else: `cosh update` and the
steps that write the local folders never upload (`refresh: deploy` in
`config/dataflow.json`), so the bucket changes only when we're about to
push. Uploading first means the new page never asks for files that aren't
there yet. Between the upload and the push, the live (old) page reads the
bucket, which works for two reasons: changed files stay compatible
("Versions" below), and files the live page reads are kept ("What an
upload deletes").

The pages ask for `?v=<stamp>`: `peers.end` (the data's end) for the
Feedback Index, the newest quarter for Review Load. A new week or quarter
is a new cache key, so browsers and Cloudflare's cache fetch it fresh.

## Uploading

`publish` syncs every prefix in `config/r2.json`, and any retired prefix
still in the bucket; name prefixes to sync only those (`publish
review-load/people/v2`). `sync <dir> <prefix>` does any one folder.

It compares each local file's sha256 with the manifest, uploads the
changed ones (16 requests in flight by default, each worker keeping its
HTTPS connection open between requests; retrying 429s, 5xx and network
errors), deletes what the live site no longer reads (below), and saves
the manifest every 500 objects, so a stopped sync resumes where it was.
It never lists the bucket, so the manifest is the truth about what's
there: if objects are changed by hand in the dashboard, delete the
manifest's entries for them (or the whole prefix's) and sync again.
`--dry-run` prints what would change.

Speed is set by the number of requests, not bytes: the files are small.
The first full upload of the threads (32,676 files, 400 MB) took 45 minutes
with 4 requests in flight and a new connection for each (about 12 a
second, 2026-11-14). With connections kept open and 16 in flight, it runs
at about 65 objects a second. That costs argus little (the workers mostly
wait on the network), and the serial-request rule covers Gerrit and
googlesource, not our own bucket.

A sync records the bytes it actually sent, and a file that vanishes during
it is left for the next run, so a step rewriting a folder mid-sync costs a
rerun, not a wrong manifest. And `publish` and the steps that write its
folders (review-feedback, review-load, review-threads, unless given a
scratch `--people-out`/`--out`) take `data/private/r2.lock`, so one waits
for the other: an upload never reads a folder being rewritten. Code from
before the move (a stale worktree) takes no lock and writes its own
per-person files; run such experiments with scratch output folders.

## What an upload deletes

An upload keeps what the live site still reads and deletes anything older:

- The live site is the one the last push deployed. It reads the files of
  the newest publish that began before that push. `cosh.r2` takes the push
  time from the reflog of `origin/main` in the main checkout, which a push
  (or a fetch) of `main` updates.
- The manifest records, for each object, when its local file was last seen
  at a publish. An object whose file is gone is **kept** if it was still
  there at the live site's publish, and **deleted** if it was already gone
  then.
- So a file dropped from the data stays in the bucket until a publish
  without it has been deployed; the next publish after that deletes it. At
  most, the bucket holds the live site's files plus the new ones.
- Publishing twice before a push is fine: the live site's publish is still
  the newest one before the last push, so nothing it reads is deleted.
- If the push time can't be told (no reflog) or no publish has been
  deployed yet, nothing is deleted.
- A prefix dropped from `config/r2.json` (a format moved to `v2`) is
  retired the same way: kept while the live page may read it, and deleted
  by the first `publish` after a page that doesn't read it is live. A
  prefix may sit inside another (`review-feedback/threads/v2` inside the
  retired `review-feedback/threads`): each object belongs to the innermost
  prefix, so retiring the outer one never deletes the inner one's files.

## Versions: add compatibly, rename on a break

A prefix names a file format (`people/v2`), not a week of data:

- **Weekly data keeps its names.** Each run rewrites the files that
  changed under the same keys (the files of people with changes this
  half-year), and a new person only adds a file.
- **Added data is compatible.** A new field in a file, or a new kind of
  file, stays under the same prefix: the pages ignore fields they don't
  know, so the live page keeps working on the new files. Write the code
  that way: a new field is optional for the reader.
- **Only a change the live page can't read moves to a new prefix**:
  removing or renaming a field, or changing what one means. Write the new
  format to a new prefix (`review-feedback/people/v3` in `config/r2.json`
  and `web/src/r2.ts`) and deploy (publish, then push). The old prefix
  stays while the live page reads it; the first `publish` after the new
  page is live deletes it ("What an upload deletes"). The local folder
  name stays the same.

## Local copies on localhost

Pages served from this machine (`npm run serve`, `npm run dev`, the tests)
read `r2/<prefix>/...` from their own server instead of the bucket
(`web/src/r2.ts`). Vite serves those from the local folders, gzipped as R2
serves them (`r2Local` in `web/vite.config.ts`), so new files can be checked
before they are uploaded. It serves only names of the bucket's form
(`<1–2 folders>/<32 hex>.json`) under the prefixes in `config/r2.json`: the
same files anyone can fetch from the bucket by name. A file missing locally
is a 404, never fetched from the bucket: the site runs in one of two modes,
local (pages and data from this machine) or deployed (pages from GitHub
Pages, data from R2), never a mix, so a missing or stale local file shows
up instead of being masked by the published copy. The data folder is
`COSH_DATA_DIR`, else the main checkout's `data/private`, also from a
worktree.

## Setting it up again from scratch

1. On the laptop: create the bucket `cosh`, add the custom domain
   (the zone must be on Cloudflare), set the CORS policy above, leave
   `r2.dev` off.
2. Add the cache rule for the hostname, and the
   budget alert.
3. Create the token (Object Read & Write, this bucket only, IP filter) and
   write `~/.secrets/cosh/r2.json` on argus:
   `install -m 600 /dev/null ~/.secrets/cosh/r2.json`, then an editor.
4. Delete `data/private/r2-manifest.json` and
   `data/private/r2-publishes.json` (they describe the old bucket), then
   run `python3 -m cosh.r2 publish`.
