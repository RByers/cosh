# Review that leads to a change: research notes

Status: research only (2026-11-04). Nothing here is in the pipeline or the
UI yet. Everything below comes from data already on disk (`derived.sqlite`
and the stored NoteDb meta refs). No fetching was done.

## The question

Today's metric counts review comments. But a comment isn't valuable in
itself: a stream of nits, or questions the author has to stop and answer,
can cost more than it returns. What we would really like to measure is how
much each person (and org) **drives improvements to the code**. A narrower
first step is to count only review that **led to a code change**. This note
looks at ways to detect that, tests each against real threads, and
recommends what to build.

## Summary

1. **Owner replies like "Done" are not brittle. They are the strongest
   signal we have, and it costs nothing.** Gerrit's reply buttons leave fixed
   strings (`Done`, `Acknowledged`, `Fix applied.`, `Marked as
   resolved.`). The owner's first reply is a "Done"-type reply on
   **43.5% of reviewer-started threads**, and on **60%** of the actionable
   ones (posted unresolved, not an approval). A bare `Done` is 64% of those
   replies.
   - **Precision:** in a hand-read random sample of 50, every one matched
     a real change (≈100%).
   - **Recall:** about **75%** of the threads that led to a change in the
     CL. Most of the rest are free-text replies ("Good point, moved it
     to …").
2. **"A new patchset followed the comment" is useless on its own.** A
   code-changing patchset follows 97% of threads, whatever the reply, and
   only about 21% of the code-changing uploads that follow a CL's first
   review are tied to an addressed thread. Most churn between patchsets
   is the author's own iteration.
3. **Line counts from patch diffs would mostly measure the wrong thing,
   and we don't have the diffs** (NoteDb holds patchset SHAs, no code).
   Attribution itself is easy at the level of an upload round: 95% of the
   uploads that answer "Done" replies answer a single reviewer. But
   crediting all the lines changed in that round would credit the author's
   own churn. And line counts don't track value: a one-line use-after-free
   fix outweighs a 200-line rename. Diffs are worth a **small, approved
   validation sample** (about 300 requests), not a bulk fetch.
4. **A "Done" count is not a value measure either.** Nits are 13% of
   threads but 23% of Done threads (78% of nits get "Done"). Of 50
   Done threads read by hand: about 34% style, naming or cleanup, 20% docs,
   comments or commit message, 14% tests, 14% design or structure, and 18%
   correctness or bugs. A plain Done count rewards asking for easy changes.
5. **Org shares barely move; individual rankings move a lot.** In scope,
   the non-Google share is 8.87% by comments and 9.79% by Done threads, and
   Microsoft's goes from 6.86% to 8.02%. Among the 200 most active reviewers,
   Done threads per comment ranges 2.4× (p10 0.24, p90 0.58). Only 40 of the
   top 50 by comments are in the top 50 by Done threads. A reviewer's rate
   is a stable trait: split-half r = 0.89, and 0.74 after adjusting for the
   owners they review.
6. **Recommendation, in phases:**
   - (a) Add an *addressed threads* metric from the reply text (no fetch).
   - (b) Use a small LLM pass over the ~25% of threads with free-text
     replies, both to recover the missed changes and to tag substance
     (bug, test, design, docs, style), so nits can be weighted down.
   - (c) Optionally, with approval, validate on a few hundred patchset
     diffs.
   - Don't build a lines-changed metric.

## Data and method

- **What NoteDb gives us for free.** Each comment in the notes JSON has
  `parentUuid` (so threads can be rebuilt), `unresolved`, file, line,
  `range`, `patchSetId`, `revId` and `writtenOn`. Each patchset upload is a
  meta commit with its time and uploader, its `Patch-set-description`, and
  Gerrit's change-kind note on the "Uploaded patch set N" line:
  - `Uploaded patch set N.` means a **rework** (the code changed);
  - `Patch Set N-1 was rebased.` means a trivial rebase;
  - `New patch set was added with same tree, parent tree, and commit
    message.` means no change;
  - `Commit message was updated.` means only the message changed.

  Over the sample, uploads were 120k rework, 16k rebase, 3.6k no-change
  and 2.2k message-only, plus 21k initial uploads. There is **no code and
  no diff** (`storage-design.md`).
- **Sample.** Every human-owned CL with comments that closed in
  2026-W36..W44: 25,840 CLs, 21,086 of them with at least one
  reviewer-started thread, and **82,918 reviewer-started threads**. A
  thread starts with a root comment by a non-owner, non-bot account that
  didn't upload a patchset and isn't `autogenerated:`. "Owner side" means
  the owner plus anyone who uploaded a patchset (co-authors). 29% of these
  threads are in the path scope (`config/paths.txt`).
- **Owner reply classes**, from the owner side's first reply in the thread
  (`reply_class` in `scripts/review_impact_stats.py`):
  - **done**: starts with done, fixed, updated, removed, changed, added,
    renamed, applied, "good catch", …
  - **ack**: `Ack`, `Acknowledged`, `OK`, `Thanks`, … with nothing else.
  - **later**: mentions a follow-up, a separate CL, a TODO or a bug.
  - **discussion**: any other text.
  - **none**: no reply from the owner side.
- **Hand labels.** I read random threads from each class and judged
  whether each led to a change in the CL, from the thread text alone (with
  no diff to check against):
  - 50 done, 50 discussion, 30 with no reply and 20 ack;
  - the 50 done threads were also labelled by substance.

  These are judgments with small n, good for rough proportions only.

Scripts (offline, read-only, a few seconds per run):

```
COSH_DATA_DIR=<main checkout>/data/private \
  python3 scripts/review_impact.py --weeks 2026-W36:2026-W44 --out threads.jsonl
python3 scripts/review_impact_stats.py threads.jsonl     # reply classes, rework timing, org table
python3 scripts/review_impact_confound.py threads.jsonl  # owner habit, attribution rounds, same-org
python3 scripts/review_impact_rank.py threads.jsonl      # org shares and reviewer ranks by measure
```

`threads.jsonl` holds comment text, so keep it in a scratch directory. It
is rebuilt in about 25 s.

## Ideas and what the data says

### 1. Owner reply text ("Done")

| Owner's first reply | All threads | Share | A rework upload followed | Rework upload within 1 h of the reply |
|---|---:|---:|---:|---:|
| done | 36,084 | 43.5% | 99.8% | 86% |
| ack | 974 | 1.2% | 97% | 71% |
| later (follow-up / TODO / bug) | 2,323 | 2.8% | 97% | 70% |
| discussion (free text) | 20,053 | 24.2% | 97% | 72% |
| none | 23,484 | 28.3% | 92% | — |

Among actionable threads (unresolved, not approvals), done is 60%,
discussion 31%, none 3.6% and later 3.6%.

- The most common first replies are `Done` (23,138), `Done.` (1,701),
  `Acknowledged` (790), `done` (176), `Fix applied.` (166, from applying
  a suggested edit), `Done!`, `Removed.` and `Marked as resolved.`. These
  look like Gerrit's reply buttons and habits built around them. That is why
  the signal isn't brittle: most owners click a button.
- **Precision:** all 50 hand-read done threads matched a plausible change
  ("Done", "Added test", "Done. Made `OnUsbDeviceConnected` a member
  method"). Only 0.2% have no rework upload afterwards.
- **What the regex misses:**
  - **discussion (24% of threads):** of 50 hand-read, 26 led to a change
    in the CL, 2 to a follow-up CL, 19 were answered or pushed back on
    with no change, and 3 were unclear. So about half are real changes in
    free text ("Thanks for the suggestion… Updated the code to make it a
    free function").
  - **ack (1%):** about half look like nits that were fixed and replied to
    with the Ack button; the rest are FYIs and LGTMs.
  - **none (28% of all threads, but 3.6% of actionable ones):** mostly
    approvals and thanks. The actionable ones were mostly on CLs that were
    never reworked afterwards (abandoned or stalled).
- **Estimated recall:** changed-in-CL threads come to about 43.5%
  (done) + 12.6% (half of discussion) + ~1% (ack, none) ≈ 57% of threads.
  The done class catches about 43.5 / 57 ≈ **75%** of them.
- **Owner habit.** Owners differ in how often they type "Done" (Done-rate
  p10 0.38, median 0.60, p90 0.80 among owners with ≥20 actionable threads;
  no owner never does). A reviewer's Done-rate correlates r = 0.35 with the
  average habit of the owners whose CLs they review, and owner habit
  explains under half of the spread between reviewers (sd 0.087 of 0.136).
  After subtracting each thread's owner propensity (leaving the reviewer
  out), the reviewer residual still has split-half r = 0.74. So it is a real
  trait of the reviewer, but the metric should adjust for owner habit or at
  least be read with it in mind.
- **Same-org review** doesn't change the rate much (Google 0.60 same-org
  vs 0.59 cross-org; Microsoft 0.59 vs 0.58). Small orgs are noisy (Intel
  0.77 vs 0.36 on 31 and 25 threads).

### 2. "A new patchset followed the comment"

A rework upload follows 97% of discussion threads and 92% of threads with
no reply, almost as often as done threads (99.8%). CLs average **5.7
rework uploads** each. So "something changed after the comment" says
almost nothing.

Timing helps a little. 86% of done replies fall within an hour of a rework
upload, against 72% of discussion replies. The done replies mostly come
*after* the upload (27.8k after vs 3.4k before, within the hour): the owner
uploads and then clicks Done. But timing can't separate the discussion
threads that led to a change from those that didn't.

### 3. Patchset diffs and lines changed

What diffs would add:
1. Ground truth for the ambiguous ~30% (discussion, ack, none): did the
   lines in the comment's `range` (or its file) change in the next rework
   patchset?
2. A size for each change.

We don't have them. Fetch options, all needing approval (ground rule 1),
and none to run alongside the backfill:

| Option | What it gives | Cost, at about 150k commented CLs and 480k reviewer threads a year |
|---|---|---|
| `GET /changes/N/revisions/K/files/F/diff?base=K-1` per thread | Line-level: did the commented range change? | one REST request per thread checked. A 300-thread validation sample is about 300 requests (~5–10 min at 1 s). The whole year would be ~480k requests: no |
| Batched `q=change:A OR …` with `o=ALL_REVISIONS&o=ALL_FILES` | Per-file line counts of every patchset against its parent, so whether each file changed between patchsets. File level only | about 1.5–3k requests a year at 50–100 CLs each, but `ALL_FILES` on every revision is heavy server-side (`gerrit-api-research.md` warns against it) |
| `GET /revisions/K/files?base=K-1` per rework upload | Which files changed in each round, with line counts | about 380k requests a year (65k rework uploads after first review in 9 weeks): no |
| Blob-less git fetch of patchset refs | File names per patchset; line diffs need blobs | a large first tree fetch; no line counts without blobs |

**How credit would be assigned with diffs.** A round runs from one rework
upload to the next. The round's changed hunks would be credited to the
threads addressed in it, by overlap with each thread's file and line
range, and anything unmatched to nobody. With no diffs, credit the round
to the Done replies posted around it. Either way, attribution is easy:
95.2% of the uploads with Done replies within an hour answer exactly one
reviewer, 4.6% two, and 0.2% three or more.

**Why lines changed is the wrong unit anyway:**
- Only about 21% of the rework uploads after a CL's first review have a
  Done reply within an hour. That is a lower bound (some replies come
  later, and free-text replies aren't counted), but most churn after
  review is the author's own iteration, CQ fixes and rebases with
  conflicts. Crediting patchset deltas to reviewers would hand them that
  churn.
- Even the lines that a review did cause track value poorly. From the
  hand-read sample: "Delete this method. It is not used" removes many
  lines; "this will run into a DCHECK failure" or "prevents a UAF … but
  ClickErrorDialogMoreDetailsForDevtools() also calls ShowModalDialog()"
  change one or two. A size-weighted metric would reward the cleanup over
  the bug.

So diffs are useful for **validation**, not as the metric. The cheap,
high-value use is about 300 line-level diff requests for hand-labelled
discussion, ack and no-reply threads. That would measure the reply-text
classifier's recall against real code instead of my reading of the text.

### 4. LLM classification of the thread text

We already store the text, so this costs compute, not server load. Only the
~25% of threads with free-text first replies (discussion and ack) need it:
about 21k threads in 9 weeks, about 120k a year, averaging 480 characters
(roughly 120 tokens, plus a prompt). That is on the order of 20–30M input
tokens a year, well within a small, cheap model. The three-year range is
three times that.

Two uses:
- **Did it lead to a change?** The 50 discussion threads were easy to label
  from the text in most cases (3 of 50 unclear). The remaining hard cases
  are "discussed offline" and "will do", which no method resolves without
  diffs.
- **Substance tags** for done threads too: bug or correctness, test,
  design or API, docs or comments, style or naming. The root comment
  alone mostly decides it, and `nit:` / `optional:` prefixes get 13% of
  threads for free.

Caveats: model labels need a hand-labelled check set, about 200 threads.
Labels can drift between model versions, so pin the model and store the
labels with a version, like `metric_version`. Outputs belong in
`derived.sqlite`, and the inputs never leave the box except to the model
API. All of the text is public Gerrit data.

### 5. Substance and the "value-destructive" side

What the Done threads asked for (50 hand-read, approximate):

| Kind | Share | Examples |
|---|---:|---|
| style, naming, cleanup | ~34% | "Nit: Restore this whitespace", "ICU -> Icu", "pls extract this into a variable" |
| docs, comments, commit message | ~20% | "Update commit message?", "Could you add one-line descriptions?" |
| tests | ~14% | "Please add unit-test coverage to `CancelPendingFaviconRequests()`" |
| design, structure | ~14% | "this helper probably belongs in the UI layer", "There's too much python" |
| correctness, bugs | ~18% | a DCHECK failure on re-extract, a UAF path, a metrics bug from 8-/16-bit string sizes, a dropped legal message on update |

Signals for review that costs more than it returns:
- **Nits:** 13% of threads and 23% of Done threads. Weight them down or
  report them separately.
- **Answered questions with no change:** ~38% of discussion threads. Some
  are valuable (knowledge transfer, reviewers checking assumptions); some
  are churn. Text alone can't tell these apart reliably.
- **Pushback that the reviewer accepts** ("I'd rather not… because …" /
  "Acknowledged"): visible in the threads, and a candidate negative signal,
  but it is hard to judge as noise rather than legitimate checking.
- **Not measured here:** the time cost. That would be the rounds a reviewer
  adds, their first-response latency and the attention-set dwell time
  (`Attention:` footers in NoteDb hold it). It is all computable offline
  and would give a "cost" side to set against the "value" side.

### 6. AI findings

8% of threads are self-declared AI comments, or a human forwarding an AI
finding ("Please fix this WARNING reported by Chromium Code Review Agent",
"[🤖]", "AI review:"). Their Done-rate is 66%, against 44% overall. If
"led to a change" becomes a metric, forwarded AI findings will boost the
forwarder. That may be fine (they chose to raise it), but it should be
reported as a subset, like `ai_comments`.

### 7. Effect on the existing picture

In scope, CLs closed 2026-W36..W44:

| Org | Comments | Threads | Actionable threads | Done threads |
|---|---:|---:|---:|---:|
| google.com | 91.13% | 91.16% | 90.24% | 90.21% |
| microsoft.com | 6.86% | 6.90% | 7.98% | 8.02% |
| igalia.com | 0.53% | 0.51% | 0.50% | 0.55% |
| opera.com | 0.52% | 0.49% | 0.54% | 0.64% |
| intel.com | 0.39% | 0.40% | 0.31% | 0.30% |
| gmail.com | 0.33% | 0.33% | 0.25% | 0.20% |
| **non-Google** | **8.87%** | **8.84%** | **9.76%** | **9.79%** |

(These shares are of threads on CLs that closed in the window, so they
don't match the headline, which is by comment week.)

- **At the org level,** the comment count is already a fair proxy. Done
  threads raise Microsoft and Opera slightly, and lower Intel and gmail.com.
  Most of the shift comes from dropping approvals and FYIs (the
  "actionable" column), not from the Done filter itself.
- **At the reviewer level,** it matters much more:
  - Spearman 0.77 between comments and Done threads over the top 200
    reviewers;
  - 40 of the top 50 shared;
  - Done threads per comment from 0.24 (p10) to 0.58 (p90).

  The leaderboard is where a "led to a change" metric would change what
  people see.

### 8. Ideas considered but not tested

- **Authored code.** The most direct measure of "driving improvements" is
  landed CLs by author, which we already list. Review-driven changes could
  be shown next to it, not instead of it.
- **Reverts.** CLs whose subject is `Revert "…"` can be matched to the
  original. A reviewer who approved CLs that were later reverted, or who
  flagged the problem first, is a quality signal. It is confounded, and
  approvals are mostly vote-only, which metric_version 5 dropped.
- **Abandonment after review.** 6.5% of reviewed CLs were abandoned. A
  review that stops a bad CL is valuable (the reason abandoned CLs count
  today), but text is needed to tell "don't do this" from an author who
  moved on.
- **Follow-up CLs.** "later" replies (2.8%) and post-merge comments that
  lead to a fix in another CL. Linking them needs CL descriptions
  (`crrev.com/c/N` links), which the listing has for merged CLs.
- **Gerrit ported comments** (`/revisions/K/ported_comments`) show where a
  comment lands on a later patchset. It might indicate whether the
  commented lines changed without fetching a diff. Unverified, and it is
  still one request per CL.
- **A review that finds nothing** still has value (an expert's +1), but it
  stays invisible to any "led to a change" metric, as it already is to the
  comment metric since metric_version 5.

## Recommendation

1. **Phase 1: an "addressed threads" metric (offline, no fetch).**
   - Count a reviewer-started thread whose root was posted unresolved and
     whose first owner-side reply is Done-type, including `Fix applied.`.
   - Credit it to the reviewer who started the thread, in the week of the
     owner's reply.
   - Report `nit:` / `optional:` threads as a subset, so a weighted
     variant is possible.
   - Offer it as a selectable metric next to comments; the headline stays
     comments until the user decides otherwise.
   - Show a per-reviewer addressed rate (addressed ÷ actionable threads)
     on the leaderboard hover card.
   - `derive` needs `parent_uuid` and `unresolved` on `comments`, an
     owner-side flag, and a reply class. The thread logic is in
     `scripts/review_impact.py`.
   (Evaluated in `docs/comment-classifier.md`: on 400 labelled threads the
   regex scores precision 0.98 and recall 0.78, and adding Haiku for the
   rest brings recall to 0.99.)
2. **Phase 2: an LLM pass over free-text replies (offline, compute
   only).**
   - Classify the discussion and ack threads (~25%) into changed in this
     CL / follow-up / no change. That should lift recall from ~75% towards
     ~95%.
   - Tag every addressed thread's substance (bug, test, design, docs,
     style).
   - Validate against about 200 hand-labelled threads first.
   - Version the labels.
3. **Phase 3 (optional, needs approval):**
   - After the backfill finishes, fetch about 300 line-level patchset
     diffs for a stratified sample of threads.
   - Measure the classifier's precision and recall against real code
     changes.
   - Don't fetch diffs in bulk.
4. **Don't** build a lines-changed metric, or credit patchset deltas to
   reviewers.

## Limitations of this analysis

- One 9-week window, CLs that closed in it, all paths. The org table is
  in scope only.
- Hand labels are one reader's judgment from text, with n = 20–50 per
  class. The proportions are rough (±10–15 points).
- "Owner side" includes anyone who uploaded a patchset. Co-reviewers who
  upload on someone's behalf would be missed as reviewers.
- The regex classes are English-only and prefix-based. "Ack" covers only
  short acknowledgements; "Acknowledged. Removed …" counts as discussion.
